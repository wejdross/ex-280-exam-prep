# Task 27 — Internal TLS and re-encrypt route (15 points)

In project `ex280-t27` (create it if it doesn't exist). Nothing in this task requires you to
generate a certificate — the cluster issues both of them.

- Create a Service named `secure-app` on port `8443` (targetPort `8443`, selector
  `app=secure-app`) and have **OpenShift issue its TLS certificate automatically** into a
  Secret named `secure-app-tls`. Do not create that Secret yourself, and do not run `openssl`.
- Deploy `secure-app` (1 replica, image `registry.access.redhat.com/ubi9/python-311:latest`,
  label `app=secure-app`) with that Secret mounted at `/etc/tls`, whose container terminates
  TLS itself on port `8443` by running exactly this command (copy it verbatim):

  ```yaml
  command: ["python3","-c","import http.server,ssl;ctx=ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER);ctx.load_cert_chain('/etc/tls/tls.crt','/etc/tls/tls.key');s=http.server.HTTPServer(('0.0.0.0',8443),http.server.SimpleHTTPRequestHandler);s.socket=ctx.wrap_socket(s.socket,server_side=True);s.serve_forever()"]
  ```

- Expose it with a Route named `secure-app`, hostname `secure-app.apps-crc.testing`, using
  **`reencrypt`** termination: the router must terminate the client's TLS and then open a
  *new*, verified TLS connection to the pod. The router must be able to validate the pod's
  certificate — supply the appropriate CA as the route's `destinationCACertificate`.

Your solution will be verified by checking that `secure-app-tls` exists and was generated by
the cluster's service CA, that the Route's termination is `reencrypt` and it carries a
`destinationCACertificate`, and by making an HTTPS request to the hostname and expecting a 2xx.

Note: `crc` on macOS has no wildcard DNS for `*.apps-crc.testing`. Grading resolves the
hostname itself with `curl --resolve`.
