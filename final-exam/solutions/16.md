# Task 16 — Rollout management

## oc path

```bash
oc new-project ex280-t16
oc create deployment rollout-app \
  --image=quay.io/redhattraining/hello-world-nginx:v1.0 --replicas=2
oc rollout status deployment/rollout-app

oc set image deployment/rollout-app \
  hello-world-nginx=quay.io/redhattraining/hello-world-nginx:latest
oc rollout status deployment/rollout-app

oc rollout undo deployment/rollout-app
oc rollout status deployment/rollout-app
```

The container name for `oc set image` comes from the image name — `hello-world-nginx` here.
Don't guess:

```bash
oc get deploy rollout-app -o jsonpath='{.spec.template.spec.containers[*].name}{"\n"}'
```

Or sidestep it entirely: `oc set image deployment/rollout-app '*'=<image>`.

## Where the history lives

There is no "revision" object. **Each revision is a ReplicaSet.** Every change to
`spec.template` creates a new one; old ones are kept scaled to 0, tagged with
`deployment.kubernetes.io/revision`. Rollback copies an old RS's pod template back.

Two consequences:

- `spec.revisionHistoryLimit` (default 10) caps retained RSs. Set it to 0 and rollback breaks.
- Changes that don't touch the pod template — scaling, editing a Service — create **no
  revision** and cannot be rolled back this way.

## Revision numbers only go up

Undo does not restore revision 1 — it writes revision 1's template as revision **3**. After
this task, history shows rows `2` and `3`, not `1` and `2`. Not a bug.

## CHANGE-CAUSE

Almost always `<none>`, because `--record` was **removed** from `oc` 4.22. Set it yourself:

```bash
oc annotate deployment/rollout-app \
  kubernetes.io/change-cause="bump to :latest" --overwrite
```

## The rest of the family

```bash
oc rollout history deployment/rollout-app
oc rollout history deployment/rollout-app --revision=2
oc rollout undo deployment/rollout-app --to-revision=2
oc rollout pause deployment/rollout-app     # batch several `oc set` edits into one rollout
oc rollout resume deployment/rollout-app
oc rollout restart deployment/rollout-app   # recreate pods with NO spec change
oc rollout cancel / oc rollout retry
```

`oc rollback` is a **DeploymentConfig-only** command and does not work on Deployments. DCs also
have `oc rollout latest dc/x`, which Deployments don't.

## YAML path

Rollback is inherently imperative. The declarative equivalent is: change `image:` back in the
manifest and re-apply. Under GitOps that's `git revert`, and `oc rollout undo` on an
Argo-managed app will be reverted by self-heal within the sync interval.

## Verify

```bash
oc rollout history deployment/rollout-app
oc get deployment rollout-app -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
oc get deployment rollout-app -o jsonpath='{.status.readyReplicas}{"\n"}'
oc get rs -n ex280-t16
```
