# Task 10 — Persistent storage

## oc path — one command creates the PVC and mounts it

```bash
oc new-project ex280-t10
oc create deployment storage-app \
  --image=registry.access.redhat.com/ubi9/ubi-minimal:latest -- sleep 3600

oc set volume deployment/storage-app --add \
  -t pvc --claim-name=t10-data --claim-size=1Gi --mount-path=/data
```

There is **no `oc create pvc`**. `oc set volume` with `--claim-size` is the generator:

| Requirement | How it's met |
|---|---|
| `1Gi` | `--claim-size=1Gi` |
| `ReadWriteOnce` | `--claim-mode` **defaults to ReadWriteOnce** — omit it |
| default StorageClass | omit `--claim-class` → no `storageClassName` → cluster default |
| mount at `/data` | `--mount-path=/data` |

`--claim-size` is the trigger that **creates** a claim. With only `--claim-name` it links an
existing one.

**Watch out:** omitting `--claim-name` silently provisions a PVC with a generated name like
`pvc-8hmc8`. Easy to leave orphaned storage behind.

## YAML path

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: t10-data
  namespace: ex280-t10
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
  # storageClassName omitted -> default class
```

then on the Deployment:

```yaml
        volumeMounts:
        - name: data
          mountPath: /data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: t10-data
```

## Access modes

| Mode | Meaning |
|---|---|
| `ReadWriteOnce` (RWO) | one **node** may mount read-write |
| `ReadOnlyMany` (ROX) | many nodes, read-only |
| `ReadWriteMany` (RWX) | many nodes read-write — needs NFS/CephFS, **not** available on CRC |
| `ReadWriteOncePod` | exactly one pod |

## storageClassName: omitted vs `""`

Omitted → use the default class. Explicit empty string `""` → **no dynamic provisioning**, bind
only to a pre-created PV. Different behaviours, and a favourite exam distinction.

## Verify

```bash
oc get pvc t10-data                 # must be Bound
POD=$(oc get pod -l app=storage-app -o name)
oc exec $POD -- sh -c 'echo persist > /data/test.txt'
oc delete $POD
oc rollout status deployment/storage-app
oc exec deploy/storage-app -- cat /data/test.txt     # persist
```

## CRC quirks seen on this cluster

- The hostpath provisioner granted **79Gi** against a 1Gi request. Normal for CRC; grade on
  `spec.resources.requests.storage`, not `status.capacity`.
- `VOLUMEBINDINGMODE: WaitForFirstConsumer` means the PVC stays `Pending` until a pod
  schedules. That is correct, not a fault.
- Reclaim policy is `Retain`, so deleting the PVC leaves the PV behind.
