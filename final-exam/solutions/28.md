# Task 28 — Application access to the Kubernetes API

## oc path

```bash
oc new-project ex280-t28
oc create sa api-reader

oc create role pod-reader --verb=get,list,watch --resource=pods
oc create rolebinding api-reader-pods \
  --role=pod-reader --serviceaccount=ex280-t28:api-reader

oc run api-client --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \
  --overrides='{"spec":{"serviceAccountName":"api-reader"}}' \
  --command -- sleep 3600
```

**`-n <ns>` before `--`.** `oc run api-client --command -- sleep 3600 -n ex280-t28` passes the
namespace flag to `sleep`, which exits non-zero and crash-loops the pod. Cost me a pod.

`oc run` has no `--serviceaccount` flag, hence `--overrides`. The alternative is a YAML pod
spec, which is cleaner if you're already writing one.

## YAML path

```yaml
apiVersion: v1
kind: ServiceAccount
metadata: {name: api-reader, namespace: ex280-t28}
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {name: pod-reader, namespace: ex280-t28}
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get","list","watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: {name: api-reader-pods, namespace: ex280-t28}
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
subjects:
- kind: ServiceAccount
  name: api-reader
  namespace: ex280-t28
---
apiVersion: v1
kind: Pod
metadata: {name: api-client, namespace: ex280-t28}
spec:
  serviceAccountName: api-reader
  containers:
  - name: api-client
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    command: ["sleep","3600"]
```

Note the RoleBinding subject for a ServiceAccount has **no `apiGroup`** — SAs are in the core
group. A User subject needs `apiGroup: rbac.authorization.k8s.io`. Getting this backwards is a
common error.

## Calling the API from inside the pod

Every pod gets a projected ServiceAccount token and the cluster CA mounted automatically at
`/var/run/secrets/kubernetes.io/serviceaccount/`. You never create a token:

```bash
oc exec api-client -- sh -c '
  TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
  CA=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
  curl -s --cacert $CA -H "Authorization: Bearer $TOKEN" \
    https://kubernetes.default.svc/api/v1/namespaces/ex280-t28/pods'
```

Three files in that directory: `token`, `ca.crt`, `namespace`. The last one is how an app
learns which namespace it's in without being told.

`kubernetes.default.svc` is the in-cluster API endpoint — always available, no DNS config
needed. `ubi9/ubi-minimal` ships `curl` at `/usr/bin/curl`, verified.

## Tokens: the modern picture

Legacy long-lived SA token Secrets are gone in recent OpenShift. Tokens are **projected,
short-lived and auto-rotated**. For a token outside a pod (testing, CI):

```bash
oc create token api-reader --duration=1h
```

Don't bake that into a pod spec — the pod's own projected token is the right mechanism and
rotates itself.

## Scoping

```bash
oc auth can-i list pods -n ex280-t28 --as=system:serviceaccount:ex280-t28:api-reader  # yes
oc auth can-i list secrets -n ex280-t28 --as=system:serviceaccount:ex280-t28:api-reader # no
oc auth can-i list pods -n default --as=system:serviceaccount:ex280-t28:api-reader    # no
```

A **Role**+RoleBinding scopes to one namespace. A ClusterRole+ClusterRoleBinding would grant it
everywhere and fail the task. `--as` works fine here because the subject is a ServiceAccount,
not a group-derived permission.

## Verify

```bash
oc get pod api-client -o jsonpath='{.spec.serviceAccountName}{"\n"}'
# expect 200 for its own namespace, 403 for another:
oc exec api-client -- sh -c 'TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token); curl -s -o /dev/null -w "%{http_code}\n" --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt -H "Authorization: Bearer $TOKEN" https://kubernetes.default.svc/api/v1/namespaces/default/pods'
```
