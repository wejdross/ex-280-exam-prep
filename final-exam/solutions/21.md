# Task 21 — ConfigMaps and Secrets

## oc path

```bash
oc new-project ex280-t21

oc create configmap t21-config \
  --from-literal=APP_MODE=production --from-literal=APP_TIER=gold
oc create configmap t21-files --from-file=assets/task21/app.properties
oc create secret generic t21-secret --from-literal=API_KEY=s3cr3t-ex280

oc create deployment config-app \
  --image=quay.io/redhattraining/hello-world-nginx:latest --replicas=1

oc set env deployment/config-app --from=configmap/t21-config
oc set env deployment/config-app --from=secret/t21-secret
oc set volume deployment/config-app --add \
  -t configmap --configmap-name=t21-files \
  --mount-path=/etc/appconfig --name=appconfig
```

`--from-file=assets/task21/app.properties` makes the **filename the key**. Using
`--from-env-file` instead would give you one key per *line*, which is a different ConfigMap
entirely.

## The oc/YAML difference worth knowing

`oc set env --from=configmap/x` does **not** write an `envFrom:` block. It expands into one
`env:` entry per key with a `valueFrom.configMapKeyRef`. Verified on 4.22:

```yaml
env:
- name: APP_MODE
  valueFrom:
    configMapKeyRef: {name: t21-config, key: APP_MODE}
- name: APP_TIER
  valueFrom:
    configMapKeyRef: {name: t21-config, key: APP_TIER}
```

Both shapes are correct and both pass this task's grader. The practical difference: `envFrom`
picks up **keys added later** on the next rollout; the expanded form only carries the keys that
existed when you ran the command.

## YAML path (`solutions/yaml/21-config-app.yaml`)

```yaml
      containers:
      - name: hello-world-nginx
        image: quay.io/redhattraining/hello-world-nginx:latest
        envFrom:
        - configMapRef:
            name: t21-config
        env:
        - name: API_KEY
          valueFrom:
            secretKeyRef:
              name: t21-secret
              key: API_KEY
        volumeMounts:
        - name: appconfig
          mountPath: /etc/appconfig
      volumes:
      - name: appconfig
        configMap:
          name: t21-files
```

## Gotchas

- Mounting a ConfigMap at a path **replaces the whole directory**. To drop one file into an
  existing directory use `subPath` — but note a `subPath` mount does not receive updates when
  the ConfigMap changes.
- Env vars **never** update on a ConfigMap change. `oc rollout restart` is required.
- `stringData:` takes plaintext and encodes for you; `data:` expects base64. Mixing them up is
  the classic Secret mistake.
