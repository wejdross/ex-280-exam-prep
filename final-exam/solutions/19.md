# Task 19 — Passthrough route / TLS backend

## oc path

```bash
oc new-project ex280-t19

oc create secret tls tls-app-cert \
  --cert=assets/tls-app/tls.crt --key=assets/tls-app/tls.key

oc apply -f solutions/yaml/19-tls-app.yaml
oc expose deployment tls-app --port=8443 --target-port=8443 --name=tls-app

oc create route passthrough tls-app \
  --service=tls-app --port=8443 --hostname=tls-app.apps-crc.testing
```

Cert and key are pre-generated in `assets/tls-app/`. `oc create secret tls` is the generator —
it produces a `kubernetes.io/tls` Secret with exactly the keys `tls.crt` and `tls.key`, which
is what the pod mounts.

## YAML path (`solutions/yaml/19-tls-app.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tls-app
  namespace: ex280-t19
  labels: {app: tls-app}
spec:
  replicas: 1
  selector:
    matchLabels: {app: tls-app}
  template:
    metadata:
      labels: {app: tls-app}
    spec:
      containers:
      - name: server
        image: registry.access.redhat.com/ubi9/python-311:latest
        command: ["python3","-c","import http.server,ssl;ctx=ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER);ctx.load_cert_chain('/etc/tls/tls.crt','/etc/tls/tls.key');s=http.server.HTTPServer(('0.0.0.0',8443),http.server.SimpleHTTPRequestHandler);s.socket=ctx.wrap_socket(s.socket,server_side=True);s.serve_forever()"]
        ports: [{containerPort: 8443}]
        volumeMounts:
        - name: tls
          mountPath: /etc/tls
          readOnly: true
      volumes:
      - name: tls
        secret:
          secretName: tls-app-cert
---
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: tls-app
  namespace: ex280-t19
spec:
  host: tls-app.apps-crc.testing
  to: {kind: Service, name: tls-app}
  port: {targetPort: 8443}
  tls:
    termination: passthrough
```

## What passthrough means

The router does **not** decrypt. It reads the SNI header to decide where to send the
connection, then forwards the raw TLS bytes to the pod. Consequences:

- The Route carries **no certificate** — there is nothing for it to hold. If you find yourself
  adding `certificate:` to a passthrough route, you've picked the wrong termination.
- The **pod** must terminate TLS, so it needs the cert mounted.
- No HTTP-level features work: no path-based routing, no header insertion, no cookie affinity.
  A passthrough Route can only route by hostname.
- `insecureEdgeTerminationPolicy` supports only `None` and `Redirect` here, not `Allow`.

## Passthrough vs re-encrypt

Both end with TLS on the wire to the pod. The difference:

| | passthrough | reencrypt (task 27) |
|---|---|---|
| Router decrypts? | no | yes, then re-encrypts |
| Route holds a cert? | no | yes (client-facing) |
| Needs `destinationCACertificate`? | no | **yes** |
| Router can do HTTP routing/headers? | no | yes |

## Verify

```bash
oc get route tls-app -o jsonpath='{.spec.tls.termination} {.spec.port.targetPort}{"\n"}'

curl -sk --resolve tls-app.apps-crc.testing:443:127.0.0.1 \
  -o /dev/null -w '%{http_code}\n' https://tls-app.apps-crc.testing/       # 200

openssl s_client -connect 127.0.0.1:443 -servername tls-app.apps-crc.testing </dev/null 2>/dev/null \
  | openssl x509 -noout -subject
# subject=CN=tls-app.apps-crc.testing  <- the POD's cert, passed through
```

A wildcard subject means the router terminated instead — wrong termination type.
