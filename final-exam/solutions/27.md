# Task 27 — Internal TLS and re-encrypt route

No `openssl` anywhere in this task — the cluster issues **both** certificates.

## oc path

```bash
oc new-project ex280-t27
oc apply -f solutions/yaml/27-secure-app.yaml     # Service (annotated) + Deployment

# the router needs the service CA to verify the pod
mkdir -p work/task27
oc extract configmap/openshift-service-ca.crt \
  --keys=service-ca.crt --to=work/task27 --confirm

oc create route reencrypt secure-app \
  --service=secure-app --port=8443 \
  --hostname=secure-app.apps-crc.testing \
  --dest-ca-cert=work/task27/service-ca.crt
```

Annotating the Service imperatively, if you'd rather:

```bash
oc annotate svc secure-app \
  service.beta.openshift.io/serving-cert-secret-name=secure-app-tls
```

## The serving certificate

One annotation, and the service-ca operator creates a `kubernetes.io/tls` Secret with
`tls.crt`/`tls.key`, SAN `secure-app.ex280-t27.svc`, **auto-rotated** before expiry:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: secure-app
  annotations:
    service.beta.openshift.io/serving-cert-secret-name: secure-app-tls
spec:
  selector: {app: secure-app}
  ports:
  - port: 8443
    targetPort: 8443
```

Do not create that Secret yourself — the grader checks for the operator's
`originating-service-name` annotation on it precisely to catch a hand-made one.

## Where the destination CA comes from

Every namespace gets a ConfigMap `openshift-service-ca.crt` containing `service-ca.crt` — the
CA that signed the serving cert. That's what the router must trust:

```bash
oc extract configmap/openshift-service-ca.crt --keys=service-ca.crt --to=. --confirm
```

## YAML path for the Route

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: secure-app
  namespace: ex280-t27
spec:
  host: secure-app.apps-crc.testing
  to: {kind: Service, name: secure-app}
  port: {targetPort: 8443}
  tls:
    termination: reencrypt
    destinationCACertificate: |
      -----BEGIN CERTIFICATE-----
      ...service-ca.crt contents...
      -----END CERTIFICATE-----
```

No `certificate:`/`key:` here — omitting them means the router serves its **default wildcard**
cert to clients, which is fine and normal for re-encrypt. Add them only if the task demands a
specific client-facing cert.

## What re-encrypt actually does

1. Client → router: TLS, terminated by the router (router's cert).
2. Router → pod: a **new** TLS connection, and the router **verifies** the pod's certificate
   against `destinationCACertificate`.

So traffic is encrypted end to end *and* the router still sees plaintext HTTP in the middle —
meaning path-based routing, header insertion and cookie-based session affinity all still work.
That's the trade-off versus passthrough (task 19), where the router sees nothing and can only
route by SNI hostname.

| | edge (06) | passthrough (19) | reencrypt (27) |
|---|---|---|---|
| Router→pod | plain HTTP | untouched TLS | new, verified TLS |
| Route holds client cert | yes | no | optional |
| `destinationCACertificate` | no | no | **yes** |
| HTTP features work | yes | no | yes |

## Verify

```bash
oc get secret secure-app-tls -o jsonpath='{.metadata.annotations.service\.beta\.openshift\.io/originating-service-name}{"\n"}'
oc get secret secure-app-tls -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -text | grep DNS:

oc get route secure-app -o jsonpath='{.spec.tls.termination}{"\n"}'

curl -sk --resolve secure-app.apps-crc.testing:443:127.0.0.1 \
  -o /dev/null -w '%{http_code}\n' https://secure-app.apps-crc.testing/    # 200
```

A **503** from the router is the signature of a wrong or missing `destinationCACertificate` —
the client TLS handshake succeeded, the router's onward connection to the pod did not.
