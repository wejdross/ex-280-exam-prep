# Task 24 — StatefulSet with non-shared storage

## There is no `oc create statefulset`

Crib the shape from `oc explain`, or from this file:

```bash
oc explain statefulset.spec
oc explain statefulset.spec.volumeClaimTemplates
```

## YAML path (`solutions/yaml/24-statefulset.yaml`)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: t24-db
  namespace: ex280-t24
spec:
  clusterIP: None            # headless
  selector: {app: t24-db}
  ports:
  - port: 8080
    name: db
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: t24-db
  namespace: ex280-t24
spec:
  serviceName: t24-db        # must match the headless Service
  replicas: 2
  selector:
    matchLabels: {app: t24-db}
  template:
    metadata:
      labels: {app: t24-db}
    spec:
      containers:
      - name: db
        image: registry.access.redhat.com/ubi9/ubi-minimal:latest
        command: ["sh","-c","echo $HOSTNAME > /data/id.txt; sleep 3600"]
        volumeMounts:
        - name: data
          mountPath: /data
  volumeClaimTemplates:      # sibling of `template`, NOT inside it
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi
```

```bash
oc new-project ex280-t24
oc apply -f solutions/yaml/24-statefulset.yaml
oc rollout status statefulset/t24-db
```

The headless Service alone is imperative-able:

```bash
oc create service clusterip t24-db --clusterip=None --tcp=8080:8080
```

## What "non-shared storage" means

`volumeClaimTemplates` creates **one PVC per replica**, named
`<template>-<statefulset>-<ordinal>`:

```
data-t24-db-0   Bound
data-t24-db-1   Bound
```

A Deployment mounting a PVC gives every replica **the same** volume. That difference is the
entire objective.

Proof:

```bash
oc exec t24-db-0 -- cat /data/id.txt      # t24-db-0
oc exec t24-db-1 -- cat /data/id.txt      # t24-db-1
```

Different values = separate volumes. Identity survives rescheduling — delete `t24-db-0` and the
replacement re-attaches the same PVC and still reads `t24-db-0`.

## Deletion semantics

```bash
oc scale statefulset/t24-db --replicas=1   # deletes pod t24-db-1; data-t24-db-1 SURVIVES
oc delete statefulset t24-db               # deletes pods; ALL PVCs survive
oc delete pvc data-t24-db-0 data-t24-db-1  # you clean up deliberately
```

Intentional: losing a database's data to a scale-down typo would be indefensible.

## Common mistakes

- `volumeClaimTemplates` indented under `spec.template.spec`. The error message is unhelpful.
- Missing `clusterIP: None` → it's a normal Service, and per-pod DNS never works.
- `serviceName` not matching the Service name.
- Trying to edit `volumeClaimTemplates` later — it's immutable. Delete and recreate
  (`--cascade=orphan` keeps the pods alive meanwhile).
- Forgetting ordered startup: pod 1 will not start until pod 0 is Ready, so a crash-looping
  pod 0 blocks everything. `podManagementPolicy: Parallel` opts out.

## Verify

```bash
oc get svc t24-db -o jsonpath='{.spec.clusterIP}{"\n"}'     # None
oc get pvc | grep data-t24-db
oc exec t24-db-0 -- cat /data/id.txt
oc exec t24-db-1 -- cat /data/id.txt
```
