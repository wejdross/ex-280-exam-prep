# Task 15 — Jobs and CronJobs

## oc path — all three are generators, no YAML needed

```bash
oc new-project ex280-t15

oc create cronjob t15-cron \
  --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \
  --schedule='*/5 * * * *' -- echo hello-ex280

oc create job t15-manual --from=cronjob/t15-cron

oc create job t15-oneshot \
  --image=registry.access.redhat.com/ubi9/ubi-minimal:latest -- echo standalone

oc patch cronjob t15-cron -p '{"spec":{"suspend":true}}'
```

## Why the suspend matters — a real bug this mock had

`oc create job --from=cronjob/X` makes the Job **owned by the CronJob**. The CronJob
controller keeps only `successfulJobsHistoryLimit` (default **3**) successful Jobs it owns and
deletes the rest. A `*/5` schedule produces three runs in 15 minutes — and then
`t15-manual` is garbage-collected.

Observed on this cluster: the task passed, then failed 15 minutes later with
`Job t15-manual not found`, with three `t15-cron-298337xx` Jobs in its place. Suspending the
CronJob after the manual trigger stops new runs, so nothing evicts your Job.

The alternatives, if a task ever forbids suspending: raise the limit
(`successfulJobsHistoryLimit: 10`), or build the manual Job without the ownership link by
exporting the jobTemplate yourself instead of using `--from`.

`oc create job --from=cronjob/X` is the command the task is really testing. It creates a Job
**owned by** the CronJob (with an `ownerReferences` entry), which is what "trigger it manually"
means — not a hand-written Job that merely looks the same.

**Quote the schedule.** `*/5 * * * *` unquoted gets glob-expanded by the shell.

## YAML path

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: t15-cron
  namespace: ex280-t15
spec:
  schedule: "*/5 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure      # or Never — 'Always' is INVALID for a Job
          containers:
          - name: echo
            image: registry.access.redhat.com/ubi9/ubi-minimal:latest
            command: ["echo","hello-ex280"]
---
apiVersion: batch/v1
kind: Job
metadata:
  name: t15-oneshot
  namespace: ex280-t15
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: echo
        image: registry.access.redhat.com/ubi9/ubi-minimal:latest
        command: ["echo","standalone"]
```

Note the double `template` nesting on a CronJob: `spec.jobTemplate.spec.template.spec`. That
is the single most common hand-authoring mistake here.

## Fields worth knowing

| Field | Object | Meaning |
|---|---|---|
| `completions` | Job | how many successful pods are required |
| `parallelism` | Job | how many run at once |
| `backoffLimit` | Job | retries before marking Failed (default 6) |
| `activeDeadlineSeconds` | Job | hard timeout |
| `ttlSecondsAfterFinished` | Job | auto-delete after completion |
| `concurrencyPolicy` | CronJob | `Allow` / `Forbid` / `Replace` |
| `startingDeadlineSeconds` | CronJob | how late a missed run may still start |
| `suspend` | CronJob | pause the schedule |
| `successfulJobsHistoryLimit` | CronJob | how many finished Jobs to keep (default 3) |

## Verify

```bash
oc get cronjob t15-cron -o jsonpath='{.spec.schedule}{"\n"}'
oc get job t15-manual -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'   # t15-cron
oc wait --for=condition=Complete job/t15-manual job/t15-oneshot --timeout=180s
oc logs job/t15-manual                 # hello-ex280
oc logs job/t15-oneshot                # standalone
oc get jobs
```

## Suspending and forcing

```bash
oc patch cronjob t15-cron -p '{"spec":{"suspend":true}}'
oc delete job t15-manual               # re-run the manual trigger from scratch
```
