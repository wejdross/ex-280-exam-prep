# Task 09 — Quota and limits

## oc path

```bash
oc new-project ex280-t09
oc create quota t09-quota --hard=pods=4,cpu=2,memory=2Gi
oc apply -f solutions/yaml/09-limitrange.yaml     # no generator for LimitRange
oc create deployment nolimits-app \
  --image=quay.io/redhattraining/hello-world-nginx:latest --replicas=1
```

`oc create quota` exists; `oc create limitrange` does **not**. That asymmetry is worth
remembering — LimitRange is one of the handful of objects you always write as YAML.

## YAML path (`solutions/yaml/09-limitrange.yaml`)

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: t09-quota
  namespace: ex280-t09
spec:
  hard:
    pods: "4"
    cpu: "2"
    memory: 2Gi
---
apiVersion: v1
kind: LimitRange
metadata:
  name: t09-limits
  namespace: ex280-t09
spec:
  limits:
  - type: Container
    defaultRequest:          # applied when the container sets no request
      cpu: 100m
      memory: 128Mi
    default:                 # applied when the container sets no limit
      cpu: 200m
      memory: 256Mi
```

## Why both, and why the order matters

They solve opposite halves of the same problem:

| | Scope | Job |
|---|---|---|
| ResourceQuota | whole project, aggregate | cap the total |
| LimitRange | per container | supply defaults, enforce min/max |

The catch that makes this a good exam item: **a ResourceQuota that caps `cpu`/`memory` rejects
any pod whose containers don't declare requests/limits.** Without the LimitRange, deploying
`nolimits-app` fails with `must specify limits.cpu`. The LimitRange fills them in first, so the
pod satisfies the quota. That is precisely what the task's third bullet is testing.

## LimitRange field names

| Field | Meaning |
|---|---|
| `default` | default **limit** |
| `defaultRequest` | default **request** |
| `max` / `min` | hard ceiling/floor per container — rejects, doesn't default |
| `maxLimitRequestRatio` | caps limit/request overcommit |

`type` can be `Container`, `Pod`, `PersistentVolumeClaim`.

## Quota scopes and counts

```bash
oc create quota best-effort --hard=pods=10 --scopes=BestEffort
oc create quota objects --hard=count/deployments.apps=5,persistentvolumeclaims=3
```

`requests.cpu`/`limits.cpu` are the explicit forms; bare `cpu` is an alias for `requests.cpu`.

## Verify

```bash
oc describe quota t09-quota          # shows Used vs Hard — the useful view
oc describe limitrange t09-limits
oc get deployment nolimits-app -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}'  # empty!
oc get pod -l app=nolimits-app -o jsonpath='{.items[0].spec.containers[0].resources}{"\n"}'       # filled in
```

That last pair is the demonstration: the **Deployment** stays empty, the **Pod** gets the
defaults. The LimitRange mutates at pod admission, not at deployment creation.
