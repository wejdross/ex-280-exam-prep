# Task 02 — Permissions

## oc path

```bash
oc new-project ex280-t02
oc adm policy add-role-to-user edit alice -n ex280-t02
oc adm policy add-role-to-user view bob   -n ex280-t02
```

That is the whole task. The knowledge being tested is **which built-in ClusterRole matches the
description**:

| Role | Can | Cannot |
|---|---|---|
| `view` | read most objects | read Secrets; write anything |
| `edit` | create/modify/delete workloads, Secrets, ConfigMaps | roles, rolebindings, quota |
| `admin` | everything `edit` can, **plus** roles/rolebindings/quota | change the project's own quota limits set by a cluster admin |

"can create, modify, delete most resources but cannot manage roles/permissions or quota" is the
textbook description of **`edit`**. Reaching for `admin` fails this task.

## YAML path

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-edit
  namespace: ex280-t02
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole          # the ROLE is cluster-scoped; the BINDING is namespaced
  name: edit
subjects:
- apiGroup: rbac.authorization.k8s.io
  kind: User
  name: alice
```

Note `roleRef.kind: ClusterRole` with a namespaced RoleBinding — that is how a built-in role
gets scoped to one project. A `ClusterRoleBinding` would grant it everywhere, which the task
explicitly forbids.

## Verify

```bash
oc auth can-i create pods        -n ex280-t02 --as=alice   # yes
oc auth can-i create rolebindings -n ex280-t02 --as=alice  # no
oc auth can-i get pods           -n ex280-t02 --as=bob     # yes
oc auth can-i create pods        -n ex280-t02 --as=bob     # no
oc auth can-i create pods        -n default   --as=alice   # no
oc policy who-can create pods -n ex280-t02
oc get rolebinding -n ex280-t02
```

`--as` works here because the subjects are **Users**. It would not work for a group-granted
permission — see task 23.
