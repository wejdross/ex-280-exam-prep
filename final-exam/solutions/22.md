# Task 22 — Scaling and autoscaling

## oc path

```bash
oc new-project ex280-t22
oc create deployment scale-app \
  --image=quay.io/redhattraining/hello-world-nginx:latest --replicas=1

oc set resources deployment/scale-app --requests=cpu=50m,memory=64Mi
oc scale deployment/scale-app --replicas=3
oc autoscale deployment/scale-app --min=3 --max=6 --cpu=70%
```

## The prerequisite that fails silently

**An HPA targeting CPU utilisation cannot work without a CPU `request`.** Utilisation is
`actual / requested` — no request, no denominator. The HPA reports `<unknown>` forever and
never scales. Nothing errors. Setting the request is step one, not an afterthought.

## `--cpu-percent` is deprecated

On oc 4.22:

```
Flag --cpu-percent has been deprecated, Use --cpu with percentage or resource quantity
format (e.g., '70%' for utilization or '500m' for milliCPU).
```

It still works. Use `--cpu=70%`.

## YAML path

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: scale-app
  namespace: ex280-t22
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: scale-app
  minReplicas: 3
  maxReplicas: 6
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

`oc autoscale` writes `autoscaling/v2` on 4.x. The older v1 shape uses
`spec.targetCPUUtilizationPercentage: 70` instead of the `metrics` list — this task's grader
accepts either.

## Reading the HPA

```bash
oc get hpa
# NAME       REFERENCE             TARGETS             MINPODS  MAXPODS  REPLICAS
# scale-app  Deployment/scale-app  cpu: <unknown>/70%  3        6        0
```

`<unknown>` for the first minute or two is **normal** — metrics-server needs a couple of scrape
intervals. Permanently `<unknown>` means no CPU request, or no metrics API.

```bash
oc get --raw /apis/metrics.k8s.io/v1beta1 >/dev/null && echo ok   # available on CRC
oc adm top pods
oc describe hpa scale-app | sed -n '/Conditions/,/Events/p'
```

Conditions to read: `AbleToScale`, `ScalingActive` (False + `FailedGetResourceMetric` is the
no-request case), `ScalingLimited`.

## Once an HPA exists it owns `spec.replicas`

`oc scale` still works but the HPA moves it back on the next cycle. Leaving a hardcoded
`replicas:` in a manifest that an HPA also manages causes a permanent sync loop under Argo CD —
which is why `replicas` is a standard `ignoreDifferences` entry.

## Verify

```bash
oc get deployment scale-app -o jsonpath='{.spec.template.spec.containers[0].resources.requests.cpu}{"\n"}'
oc get deployment scale-app -o jsonpath='{.status.readyReplicas}{"\n"}'
oc get hpa scale-app -o jsonpath='{.spec.minReplicas}/{.spec.maxReplicas} {.spec.metrics[0].resource.target.averageUtilization}{"\n"}'
```
