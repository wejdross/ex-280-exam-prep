# Task 20 — Troubleshooting

The grader seeds the break on first run:

```bash
task grade:20          # seeds ex280-t20 if not present
```

## Diagnose

```bash
oc get pods -n ex280-t20
# broken-app-... 0/1 CrashLoopBackOff

oc describe pod -n ex280-t20 -l app=broken-app | tail -25
oc get events -n ex280-t20 --sort-by=.lastTimestamp | tail -10
oc logs deployment/broken-app -n ex280-t20
```

The logs give it away:

```
nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)
the "user" directive makes sense only if the master process runs with super-user privileges
```

## Root cause

The Deployment uses `docker.io/library/nginx:latest`. That image expects to start as **root**,
write to `/var/cache/nginx`, and bind port 80. Under OpenShift's default `restricted-v2` SCC
the container gets a **random high UID** and none of that works.

This is the single most common "works on my laptop, not on OpenShift" failure, and it's why
the task exists.

## Fix

```bash
oc set image deployment/broken-app \
  nginx=quay.io/redhattraining/hello-world-nginx:latest -n ex280-t20
oc rollout status deployment/broken-app -n ex280-t20
```

Use an image built to run as an arbitrary UID. The Red Hat training image, `bitnami/nginx`,
and `registry.access.redhat.com/ubi9/nginx-124` are all fine.

The task says fix the manifest causing the problem, so changing the image is the intended
answer. Granting `anyuid` to the ServiceAccount would also make it start, but that's working
around the problem with a privilege escalation rather than fixing it — and on a real exam,
"make the insecure thing work" is rarely what's being asked.

## The general triage order

```bash
oc get pods                        # what state?
oc describe pod <pod>              # Events at the bottom — scheduling, mounting, pulling
oc logs <pod>                      # app-level failure
oc logs <pod> --previous           # for CrashLoopBackOff, the run that actually failed
oc get events --sort-by=.lastTimestamp
```

Map the status to the layer:

| Status | Look at |
|---|---|
| `Pending` | `describe` Events — no node, unbound PVC, quota rejection |
| `ImagePullBackOff` | image name, pull secret, registry reachability |
| `CrashLoopBackOff` | `oc logs --previous` — the app itself |
| `CreateContainerConfigError` | a missing ConfigMap/Secret referenced by the pod |
| `0/1 Running` | readiness probe failing |
| sandbox / CNI errors | cluster-level networking, not your workload |

`--previous` is the one people forget: on a crash-looping pod, plain `oc logs` may show the
*current* attempt's empty output while the useful error is in the previous one.

## Verify

```bash
oc get deployment broken-app -n ex280-t20
oc rollout status deployment/broken-app -n ex280-t20
```

The grader checks health **twice, 15 seconds apart** — a crash-looping pod briefly reports
Ready right after a restart, and that shouldn't score.
